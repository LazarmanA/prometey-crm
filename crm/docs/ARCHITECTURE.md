# Целевая архитектура ПРОМЕТЕЙ

## Продуктовый принцип
ПРОМЕТЕЙ должен поддерживать больше бизнес-процессов, чем типовая отраслевая CRM, но скрывать техническую сложность за понятными бизнес-сущностями.

Основной пользовательский путь:

`Клиент → Объект → Заказ → несколько единиц техники → Смены → Документы → Оплаты → Прибыль`

Для собственного парка:

`Техника → Машинист → Местоположение → Смены → ТО/ремонт → Затраты → Доходность`

## Целевые доменные модули
- `core`: компании, пользователи, роли, разрешения, подписки, аудит;
- `crm`: клиенты, контакты, лиды, звонки, задачи;
- `operations`: объекты, заказы, позиции заказа, назначения, смены, диспетчеризация;
- `fleet`: техника, машинисты, GPS-устройства, позиции, ТО, ремонт, топливо, штрафы;
- `partners`: поставщики, партнёрская техника, ставки, взаиморасчёты;
- `finance`: счета, оплаты, расходы, кошельки, задолженность, прибыльность;
- `documents`: договоры, акты, УПД, путевые листы, ЭТРН, КС-2/КС-3, шаблоны;
- `integrations`: 1С, Яндекс Карты, телефония, Telegram, email, ЭДО, банки;
- `analytics`: роль-ориентированные dashboards;
- `ai`: Prometey AI поверх разрешённых функций доменных модулей.

## Главные архитектурные правила
1. Один production frontend и одна дизайн-система.
2. API-first: веб, мобильное приложение и партнёрский кабинет используют единые контракты.
3. Multi-tenant: каждая бизнес-запись имеет `company_id`.
4. Изоляция tenant на уровне PostgreSQL RLS, а не только UI.
5. Роли и granular permissions на сервере.
6. Строковые enum-статусы вместо «магических чисел».
7. Единый `audit_log` для критичных изменений.
8. Интеграции — адаптеры; core CRM не зависит напрямую от 1С/GPS/телефонии.
9. Платные модули включаются feature entitlements на уровне компании.
10. AI никогда не имеет неограниченного прямого доступа к БД: только разрешённые инструменты/functions.

## Роли первой версии
### Руководитель
Видит всю компанию, финансовые показатели, всех менеджеров, собственную и наёмную технику, управляет модулями.

### Менеджер
Видит свои объекты/заказы и работающую на них технику; создаёт клиентов, заказы, наёмную технику, назначения и детализацию смен. Финансы компании скрыты.

### Диспетчер (следующий спринт)
Видит парк, графики, маршруты, машинистов, назначения; финансы скрываются отдельным permission.

### Бухгалтер (следующий спринт)
Счета, оплаты, задолженность, документы, обмен с 1С.

## Почему локальная версия использует JSON
Это deliberate prototype adapter: UI и REST-контракты можно тестировать без облачной инфраструктуры. После валидации `storage/data.json` заменяется на PostgreSQL repository без изменения пользовательской модели.
